# Documentation is part of delivery.

If a project cannot be set up, understood, or handed off by someone other than the original author, the delivery is not finished. Documentation is what turns one person's memory into a team's ability.

## Delivery lens

I treat setup guides, runbooks, architecture notes, and handoff docs as a core part of the engineering outcome.

## Documentation has a job to do

Good documentation should reduce friction, reduce time-to-first-win, and reduce the number of questions a new developer has to ask before they can contribute. The goal is not prose for its own sake. The goal is operational clarity.

### Onboarding

Show how to install, configure, and run the system locally.

### Operation

Describe how releases, rollbacks, and routine maintenance work.

### Handoff

Let another person take the system over without relying on hidden knowledge.

## The documentation stack

- **README:** what the project is and how to get started.
- **Setup guide:** exact steps to recreate the working environment.
- **Architecture notes:** what is connected to what and why.
- **Runbook:** how to operate and recover the system in normal and bad states.
- **Backlog notes:** what remains, what is known, and what should happen next.
- **Decision log:** why certain technical choices were made.

## What changes when documentation is treated seriously

### Teams move faster

Better docs mean fewer repeated explanations and fewer blocked developers waiting on tribal knowledge.

### Risk goes down

Clear release steps and rollback notes reduce the chance that a routine change becomes an incident.

### Ownership gets real

If the team can read the system, they actually own the system.

### Hiring becomes easier

A public site that shows how you document and explain work makes your process visible before the interview.
